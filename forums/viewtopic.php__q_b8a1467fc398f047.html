[RAS2] Diary Entry #32

by jonathan on Wed Jan 11, 2012 6:51 pm

Hi All,

I hope you've all had a great Christmas and New Years.

Since last time...

o Improved the low level graphics library
+ Support Float16 and Float32 formats
+ Uses state objects (instead of discrete states)
+ Supports rendering to a texture/raster
+ Replaced the shader system
o Further work and research on next gen renderer (NgRenderer)
o Added simple shader library
o Created new pixel handling framework
o Refactored color handling
o Sundry library improvements and bug fixes

This was a good chunk of work, but I'm still a way off of the new renderer. So that is going to be where all the effort is going to go for next time.

The majority of the work was on the low level graphics library. Generally thats twice the work or more than you'd expect because the library works with both OpenGl and DirectX, so every change and improvement has to be implemented for both systems.

It was also due to supporting both DirectX + OpenGl that the biggest extra chunk of work appeared over the month. Here's why. On OpenGl pixels are always laid out in the same way, irrespective of the machine you are on. If you have a color pixel holding red green and blue, it will be stored in memory just like that. On DirectX it's not like that - the order of the components is dependent on the endianess of the machine you are using. On PCs - that means little endian, which means everything is flipped around ie stored blue, green, red.

Previously to work around this - I just had dx formats and opengl formats, and code that convert between the two quickly. But another spanner was introduced into the works. I wanted to support Float16 and Float32 based formats - for high dynamic range rendering and other uses. In OpenGl everything works as before. On DirectX - I now have at least in principal to support the format of it being forward or backwards depending on the endianess of the machine. Worse, previously the OpenGl formats and DirectX formats were distinct - because they used a different order of components, but now for Float32/16 both OpenGl and DirectX will support the same ordering on big endian machines. I really don't want to have to have to formats which are distinct, but sometimes mean exactly the same thing - which is what I'd have if I kept the previous system.

Finally I'm getting a bit of a combinatorial explosion of formats. They are not totally easy to add. And the method I have is becoming somewhat inefficient. Previously my simplifying idea was to make all formats able to convert to a 'standard' format. In my case this was 8 bits per pixel ARGB format (basically DirectXs basic color format). When I added support for floating point components, thats no good - because if I convert a floating point value into that format - I'll lose the majority of the information. So now I have to support two 'standard' formats - UInt8 ARGB and Float32 ARGB. And the inefficiency? Well now everything has to be converted through a four color pixel format - even if it only has a single component. For example lets say I want to convert A_U8 (Alpha UInt8) to A_F32 (Alpha Float32). Heres what I'd have to do

1) Convert A_U8 to ARGB_U8 (because thats the 'standard format' that everything UInt8 based goes through
2) Convert ARGB_U8 to ARGB_F32 (because I need Float32, and I need in that format to convert back to A_F32)
3) Convert ARGB_F32 to A_F32

What a waste - all I really need to do is just expand the UInt8s to Float32s and I'm done, but I've had to do all this extra messing around.

To get around these problems I did two things
1) Standardized on the OpenGl style - ie all formats are defined by how their components are laid out in memory
+ This makes all formats unique - although if they have more than one component generally you end up with 2 formats, one forwards and one backwards
2) Rewrote how all pixel conversions take place

Instead of my previous 'standard format' idea, I now have a more general standard format, which is a pixel can be made up of 1 to 4 of any basic type - such as UInt8, UInt16, Float16, Float32 etc. Most modern formats fit this style exactly - so to use those formats, you don't have to do anything other than specify how their memory is laid out. The code to do conversions etc will be generated automatically. Some other formats need converting to, and from this format - for example RGB565 needs to be expanded into 3 UInt8s (one for R, G, and B).

So now conversions are made up of the following phases

1) Unpack
2) Pre shuffle
3) Type convert
4) Post shuffle
5) Pack

Note that there is only ever one shuffle in an actual conversion - you choose to do it pre or post depending on what is the most efficient way to do it. Not all of these stages are needed - it depends on the conversion. For example the previous example of A_U8 to A_F32 conversion just requires 3) Type Convert. The shuffle was the most complicated part of the code. The actual process is pretty simple, but to do it fast requires lots of special cases. I wrote a test suite that would test all combinations to make sure all the special cases work - in turns out there were around 20 thousand unique combinations.

Another advantage of the approach is that type conversions can generally be very fast - as everything, is held contiguously in memory, ripe for simd. There is a complication in that you may need some memory 'workspace' to do the conversion too, but theres code that creates a little buffer that will stay in cache, and will do the conversion through that space.

So for next time - I'm focusing on the new renderer. The 'research' NgRenderer will die at some point - I see it now as a failed experiment. Once the new renderer works, I'll also be able to kill the legacy renderer that's being used by most systems.

I think now I have a firm foundation to support the new renderer, but I'll only know if my low level graphics library is up to it once I try to support shadows and the such like.

Until next time,

Jonathan

by jonathan on Mon Feb 27, 2012 4:52 pm

@Geometrian

"Why support DirectX?"

It's a reasonable question. There's a few reasons - it's the Api that I'm most familiar with, but now with all the OpenGl work I'm up to speed with that now. It is a bunch of extra work for sure, but making the low level api that I write code to be underlying api agnostic has a couple of nice benefits. It's handy for testing, if a rendering problem appears on both then I can be more confident that the problem is in higher level code. If not then it's more likely something low level. Much like making your code cross platform requires a more rigorous approach so does making it work across apis. So if I want to support OpenGlEs or a console etc, it's going to be much easier. I also think DirectX leads where OpenGl follows for the moment.

Just between you me and the post I'm not really that keen on the OpenGl state machine model. I much prefer the DirectX object model - because its so much more obvious about what state is and where it goes. I've on a few occasions had to use a OpenGl debugger to try and figure out whats going on. On the plus side for OpenGl although the code is somewhat of a mess - I have a single OpenGl driver that covers Gl from 1.0 through 2.0 and beyond. Whereas with DirectX I need completely separate implementations for each target version. And the other huge plus - is that I get OpenGl on most platforms.

The big downside of course is more work. Some of the work I can't avoid - in that I have to write HLSL and GLSL shaders, which is a bit dull. I'm really into trying to be platform agnostic - so that's just part of the pain.

Cheers,

Jonathan
