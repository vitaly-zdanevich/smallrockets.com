[RAS2] Diary Entry #10

by jonathan on Sun Feb 07, 2010 7:53 am

Hi,

here's the first update for 2010. My plan of being complete by the next update has (somewhat predictably unfortunately) fallen through. The main things I worked on were

o Handling game 'state'
o Fading between game states (fogging and blending out)
o Building 64 bit version
o Game logic - as in game progression, as well as progression within a level
o Ancillary screens - such as start up logo, scrolly text, etc

The 'game states' in this context is having a way to encapsulate the different modes of a games operation. In Tower when you start the game, the first thing that happens is it shows you a kind of demo - showing the lines you want, after you press a key you can play the game properly. If you win the game goes into a different mode where it fills up the tower with blocks. Previously this was handled with 'enum and switch' - this worked of course, but it was very hard to work out what was going on. It also has issues in terms of where the data associated with the mode is stored. With enums - the data generally ends up being global, and since every bit of data becomes global it makes it even more confusing what is associated with what.

The more object orientated way of doing it is to have objects which handle each state. When done this way the data associated with a state can be held inside of an object representing that state.

This alone though isn't enough. When in the menus you have a demo of the game running in the background. Over the top of that you have menus - the each menu is a different state. And if you select a menu option the game may fade out/in into the new mode. Well that's 3 states simultaneously right there. The solution was to have a stack of states. For fading, you have a problem of when you select, you stay in the state until the fade completes - that's something in the future. You could make this by when the option is selected store in the object what was selected, kick off a fade, and when the fade completes, perform the option. Doing things this way would require every menu that did this to have this extra logic, which is extra effort and extra messy. To work around this I created a simple 'language' where you describe all the state changes you want to happen as a string. When the fade out is complete, you run the strings instructions, and then fade in, in the new state. For example when leaving the main game you could use the string 'clearStack,push(game.demo),push(menu.main)'. Or to go another menu you could do 'change(menu.changeResolution)'.

Doing the 64 bit build went remarkably smoothly. I installed win7 64 bit - and then had to remove all assembler from the code base and make it use intrinsics instead. When running in 64 bit mode its like being on a different processor - you have more registers, you can use SSE2 instructions, pointers are 64 bits. I also had a stab at doing a Max OSX snow leopard build - but had some other issues I'll have to come back to. I'm quite pleased that I have the codebase running on 3 different 'processors' - PowerPC, x86, and x64 (86 bit x86).

The game logic - was trying to encapsulate the gameplay, and the game progression. I'm not sure my solution is so great - I basically have two objects one to represent the overall GameLogic (and progression), and another to represent the state in a level. I had a lot of issues about how the PlayLogic should work. For example if the player wins (as defined by the PlayLogic) should it just inform the current game state, and then it handle it? For maximum flexibility in the end I made the PlayLogic just do everything - so the actually game state really does very little apart from calling the PlayLogic. I'm not complete on the overall GameLogic, although that shouldn't take long now I've got a solution on PlayLogic.

I wonder if all this stuff is run of the mill in normal game development. I've been more involved with middleware over the years, so a lot of this stuff is new to me (like the stack state idea - I found that on the web when I got stuck). You live and you learn for sure.

Now I'm getting closer to the end I can see theres still a few fairly large bits to sort out, so I'm not going to say I'm going to be done by next time. All I can promise is I'll be considerably closer

There 80/20 rule seems to apply here - in that the last 20% of a job seem to take 80% of the effort.

So here's to a great 2010 and releasing some games!

Jonathan

Linux's user experience is utterly inconsistent, not helped by the FSF's philosophy of providing choice for its own sake, regardless of whether the choice is meaningful in any way. How many window managers and desktops do users really need? Apple's answer is "one". (Two if you count their Jef Raskin-inspired "zoomable" iPhone / iPad interface.)

And Apple is right. From a user education and interaction design perspective, there aren't actually all that many correct ways to do human interaction design. So rather than diluting all your resources and building umpteen different takes on everything, you'd be far better off coordinating all that effort onto just one or two takes—one for each market—and getting a better product.

But the FSF doesn't work that way: most of its supporters are the kind of people who love programming for its own sake. If a project is "cool", it'll get lots of programmers. When it's less cool, it gets very few—or none. So the cool stuff gets all the focus, while the boring, but very, very useful, stuff gets far less attention. (Design by committee is also a natural result of the FSF approach.)

There's very little evidence of genuine attention to detail. No single person carries a single vision of the end product. The result is a mish-mash of incompatible APIs at the GUI level. Do we build our graphical installer for KDE? For GNOME? Can we assume there's even an installation of the X window manager? And which version of said manager should we assume is present?

The difference between the FSF approach and the commercial approach is that the latter has to do the boring stuff too, and they give it the same attention as everything else. In the FSF's community, that boring stuff is done grudgingly at best.
