by stimarco on Mon Jun 11, 2007 3:00 pm

May I interject?

Jon isn't just building a new game: he's building a completely new 3D graphics engine, a new GUI library -- Vista pretty much kills the old one stone dead -- as well as other tools, editors and the like, so that future games will be a _lot_ quicker and easier to produce.

The ultimate intention is to have a cross-platform engine and toolchain so we can also release games on other platforms too. (E.g. Mac and, if possible, some of the newer consoles.)

The old engine is getting on for eight years old and supporting it is no longer financially viable, hence Jon has a plan to port all his old games to the new engine. (Or at least those that actually sold in any numbers.) A seven-year shelf-life -- many of our games were released in 2000 and are still selling -- is practically unheard of in the games industry; Jon's treading new ground here.

This isn't just RAS 2 he's working on: it's building a completely new middleware toolchain from scratch. It's the difference between building a single tower block and constructing a whole new town. And Jon really is doing all this on his own, while holding down a day-job and maintaining the server to cut down on forum spammers.

Jon would be the first to admit that this is taking a heck of a lot longer than he originally planned, but this is a one-off situation. There is light at the end of the tunnel and no, it's not an oncoming train this time!

A game engine includes ALL of the following:

1. Graphics engine -- the bit that draws all the pretty planes and landscapes;

This is the really, really hard part of the job. The new engine has to be able to cope with fancy shader technologies, umpteen different graphics cards, different memory capacities, older 4:3 aspect displays, newer 16:9/16:10 aspect (i.e. "widescreen") displays, fancy post-processing effects and all the other fancy display stuff a modern game needs.


2. Audio engine -- as above, but for sounds.

This is probably the hardest to test as audio is heavily reliant on clean, clear data buses. Its data is streamed constantly from disk to memory to sound chip, so any 'traffic jams' on the computer's data connections will cause nasty glitches. (On top of that, there's also the question of surround sound, mixing sound effects with music, buffering of data, etc.)


3. Interaction engine -- the bit that reads joysticks, mice, keyboards, etc.;

Windows is the ONLY platform to have a standardised joystick-handling system built into the operating system. Neither Linux nor Apple's Mac OS X have this, so this is far from trivial. And it has to cope with joysticks dating back over 10 years, as well as with anything from a simple one-button Apple mouse to one of those insanely expensive multi-button, multi-stick flight sim joysticks.


4. GUI engine -- the bit that handles all those menus, sliders, buttons and stuff.

This has to deal with different languages too, as well as coping with running at different display resolutions and aspect ratios. Suffice to say that it's not as easy to put one together as it sounds.


5. Networking engine -- the bit that talks to other computers and lets multiplayer games happen.

Jon has admitted that the current games use a 'peer-to-peer' system, whereby communication is point-to-point, like a telephone network. However, this doesn't scale well and has all sorts of issues when you throw routers and other security systems into the mix. So Jon's writing a new system from scratch which will talk through a central server. (One up-side is that GameSpy will no longer be necessary. Another is that finding other players will be easier and you won't need to worry so much about low-level stuff like IP addresses.)

*

Those are just the basic components. Since Jon wants his new system to run on different computers, all these components have to be 'abstracted' -- decoupled from the operating system -- which adds another layer of complexity to the whole process.

And on top of all that, Jon is also building tools and utilities to make putting games together easier. These allow games to be much easier to modify, not just for us, but also for end users, should they wish to do so.

A GUI tool, for example, will allow him to put together a front-end for a game in a day, rather than having to plan it all out on paper first and type coordinates into the game, rebuild it, test it, then repeat the process until all the menus, buttons, sliders and such are working properly.

Other tools will be needed to build levels for RAS 2 (and import levels from our older games).

And then, Jon has to build the necessary back-end server infrastructure to handle networked games. Every multiplayer RAS 2 game will have to connect to this, so it's got to be capable of taking a lot of traffic.


That's a hell of a lot of work.
